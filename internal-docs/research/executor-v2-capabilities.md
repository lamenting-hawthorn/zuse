# Executor v2 capabilities audit

Inspected 2026-10-01 at commit `50bea37fe5d146701990901a878ea940c5012564`. This is source inspection of the public `v2` branch, not a deployed-service or independently executed upstream test report. Zuse production code was not changed.

## What changed conceptually

v2 is an app platform around reusable accounts, authored tools, storage, UI, and background execution. It is a substantially different embedding model from the currently integrated v1 connection engine. An account can be selected by several apps without duplicating credentials; profiles hold account selections independently of code. Apps retain source history and deployments. Owners remain product references, so Zuse must keep enforcing authorization. [domain model](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/CONTEXT.md)

## Implemented surfaces present in source

| Capability | What exists | Important boundary |
| --- | --- | --- |
| Reusable accounts and profiles | API-key and OAuth provider declarations, normalized provider identity, account reuse, multiple accounts, per-profile selections | SDK owner fields are not an authorization system; account resolution requires product checks. |
| App lifecycle | Authored TypeScript apps, editable source, retained Git source/deployment versions, copies/forks and publication concepts | Installing an app copies source; future upstream publication changes do not automatically update it. |
| MCP/code mode | `execute`, `resume`, `skills`; discovery/search and app/profile tool namespaces; approval/elicitation continuations | Code mode is a restricted interpreter. It reaches authorized app tools, not ambient network or Node globals. |
| Protocol imports | MCP HTTP/SSE; local stdio; OpenAPI and GraphQL authoring helpers | Stdio remains local. Catalog quick-add only prepares MCP when anonymous initialize or advertised OAuth establishes the connection method. Other entries require authored setup. |
| App state and UI | Typed persistent app data, query/mutation separation, reactive/live queries, private app UI | This requires app runtime/storage integration beyond the current MCP credential vault. |
| Webhooks | Subscription registration/cleanup, signed callback handling, manual setup, lifecycle reconciliation, app state and workflow access | Author verifies signatures; subscriptions pin deployment/accounts. Providers own delivery retry; Executor does not deduplicate or replay deliveries. |
| Schedules | Interval and five-field cron declarations, enable/pause/run-now, history, overlap exclusion, overdue coalescing, automatic or browser approval | Starts paused; minimum interval 60 seconds; current deployment/accounts each run. No automatic mutation replay or background elicitation. |
| Durable workflows | Named steps, retry/backoff/timeouts, sleeps, query/mutation steps, pinned code/account IDs, current credentials at each step | External writes still require idempotency. No durable human-input/event wait API in the first workflow version. |
| Hosted organization model | Organizations, groups, private/shared accounts, app use permissions separate from credential access, member choices | These are hosted product implementations, not permission rules automatically supplied by `createExecutor`. |
| Cloud/local runtime | Separate Node/workerd/cloud adapters and native Cloudflare schedule/workflow infrastructure | Bundling/checks do not prove a particular live deployment; the native integrations bring additional storage/build requirements. |

## Inference and the quoted claim

I found **no built-in inference client, model gateway, `classify` API, model billing system, or model provider integration** in the inspected SDK, app framework, MCP implementation, or app templates. Searches for inference/LLM/OpenAI/Anthropic/classification led to generic type inference and marketing material rather than a production inference facility. This is a bounded source finding, not proof that the author has no separate unpublished project.

The architecture can support the quoted use case: an authored app tool can use its selected model-provider account and invocation-scoped `fetch` to call an inference API. Code mode can call that tool alongside other tools; webhooks and scheduled mutations can perform the same inference, and workflows can make it a durable step. That is an **inference about composing existing capabilities**, not a documented first-class inference API. [app context capabilities](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/apps/src/contracts/app.ts) and [code mode implementation](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/mcp/src/implementation/execute.ts) establish the underlying seams.

Example application: receive a support-ticket webhook, invoke a model to classify its urgency, then update the ticket or notify a team. The app author/product must still supply the inference implementation, credentials, limits, cost attribution, output validation and action permissions. There is no evidence that migrating to v2 alone adds that classifier to Zuse.

The repository includes Rhys Sullivan's “We're not using enough inference” essay dated 2026-08-09. It discusses future uses of abundant inference but does not document an Executor inference SDK. I could not establish that it is the source or exact context of the user's quote. [inference essay](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/apps/marketing/src/content/blog/we-are-not-using-enough-inference.md)

## Maturity and misleading documentation

- Actual contracts, implementation and E2E files contain schedules and durable workflows even though the root README says no scheduler API and parts of app authoring docs say durable background jobs are deferred. Prefer the code and focused workflow documentation over those stale summaries. The term “V1” in the workflow guide describes its initial workflow feature version, not necessarily the old Executor product.
- `createRemoteExecutor` exists as an export but **returns `NotImplemented`**. [SDK constructors](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/sdk/src/implementation/create.ts)
- SDK package is private, source-exported and depends on workspace packages and an Effect snapshot; this is not a simple stable npm v2 upgrade. [SDK package manifest](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/sdk/package.json)
- Upstream E2E scenarios exist for workflow durability, replay authorization, schedules across restart, browser approvals and hosted schedules. Their presence provides evidence of intended behavior, but these tests were not run in this audit. [workflow durability E2E](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/e2e/tests/workflow-durability.spec.ts), [schedule restart E2E](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/e2e/tests/schedule-restart.spec.ts), [hosted schedules E2E](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/e2e/tests/hosted-schedules.spec.ts)
- Several README links point at `notes/` deliberately excluded from the public export. They cannot be treated as inspected evidence.

## Implication for Zuse

For today's connect-a-plugin use case, most visible value is still account connection, private inventory and authorized tool execution, which the existing integration already targets. v2 becomes much more valuable if Zuse intends to let agents author durable apps, reusable inference tools and automations. Preserve Zuse's public plugin contracts and isolate a v2 feasibility spike behind its backend adapter. Do not present inference/triggers as existing Zuse functionality merely because upstream v2 has the underlying app and execution model.

## Stored data detail

Each configured app has its own database retained across code updates. Account profiles do not imply separate per-profile databases: an app author must model data ownership deliberately if profiles should see different rows. `defineDatabase` declares typed tables and indexes; queries get read-only sessions, mutations get write transactions, output validation precedes commit, and browser clients can subscribe to queries. Schema changes fail closed; an explicit data-migration flow is not implemented. Invocation budgets include 64 KiB per row, 4 MiB read, 1,000 writes, and 100 index scans. [Storage guide](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/app-templates/executor/skills/app-authoring/storage.md)

Schedules are saved per app/profile and require product authority. Configuration checks a profile's subject against the actor and uses revision checks; execution hosts must supply current authority. This is background execution using stored authorization, not an agent prompt that runs only while a chat is open. [Scheduler implementation](https://github.com/UsefulSoftwareCo/executor/blob/50bea37fe5d146701990901a878ea940c5012564/packages/sdk/src/implementation/schedules.ts)
