# Executor as the backend for portable Zuse plugins

Research date: 2026-09-29. Source inspected: Executor commit `a6a7bf2090ce103e37e38858f91fdd6fbce4afb0`. No deployment or runtime integration was performed.

## Recommendation

Use Executor as the tools, account connections, and policy backend behind a Zuse-owned plugin catalog. A user connects an account once, chooses which projects/agents can use it, and compatible agents receive the same scoped MCP endpoint. This is feasible for Claude Code and Codex; support for another agent depends on its MCP capabilities and Zuse driver wiring. Executor accepts upstream MCP, OpenAPI, and GraphQL integrations. It does not make native Codex plugin packages, hooks, commands, or skills portable by itself. That packaging and agent-specific translation remains Zuse work. [Executor introduction](https://executor.sh/docs), [MCP proxy source](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/docs/mcp-proxy.mdx).

## Verified capabilities and constraints

- **License:** the repository is MIT licensed; redistribution requires retaining its copyright/permission notice. [License](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/LICENSE).
- **Self-hosting:** the published Docker setup includes the API, web console, MCP, authentication, and QuickJS execution over SQLite. Preserve `/data`, including encryption keys, and configure the public URL for OAuth/login behind TLS. Source README currently names `ghcr.io/usefulsoftwareco/executor-selfhost`; the public Docker page still names `ghcr.io/rhyssullivan/executor-selfhost`. Verify and pin an actual release image/digest before deployment. [Docker documentation](https://executor.sh/docs/hosted/docker), [source README](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/README.md).
- **Identity:** self-host supports cookies, bearer/API keys, and MCP OAuth. First signup claims ownership, then users join through invitations. The shipped host deliberately has one organization. User-owned connections are separate from organization-owned connections, but this is not a turnkey tenant-per-Zuse-customer deployment. [README](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/README.md), [single-org bootstrap](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/src/auth/seed.ts), [scope isolation tests](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/src/scope-isolation.test.ts).
- **Multiple accounts:** connections are identified by owner, integration, and name, with health and expiration metadata. One integration can have multiple personal or shared account connections. Use per-user authenticated requests; never distribute an admin/platform credential to desktop clients. [Connections API](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/core/api/src/connections/api.ts), [platform credential isolation tests](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/src/platform-credential.test.ts).
- **Catalog and management:** typed APIs expose integration metadata/auth methods, connection creation/removal/health, tool discovery, and OAuth client registration/start/callback. Toolkits restrict reachable connections and tool policies. Zuse can build its own compact catalog UI over these APIs, but Executor's integration catalog is not itself a signed Zuse plugin distribution format. [Integration API](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/core/api/src/integrations/api.ts), [OAuth API](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/core/api/src/oauth/api.ts), [toolkits implementation](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/plugins/toolkits/src/server.ts).
- **OAuth provisioning:** registered owner-scoped OAuth apps and dynamic client registration are supported. Self-hosting does not automatically provide approved OAuth applications for every external service; register provider apps where dynamic registration is unavailable and configure scopes/callbacks. [OAuth API](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/core/api/src/oauth/api.ts).
- **Approvals:** execution supports MCP elicitation and browser approval/resume. Clients without elicitation can receive an actionable unsupported result; behavior must be exercised separately for each Zuse driver. Search/invoke mode exposes discovery plus invocation without general code execution, delegates invocation approval to the client, and still enforces workspace blocks. It must not be presented as equivalent to every code-mode approval policy. [MCP host](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/packages/hosts/mcp/src/tool-server.ts), [proxy documentation source](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/docs/mcp-proxy.mdx), [selfhost MCP tests](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/src/mcp/mcp.test.ts).
- **Host exposure:** self-host uses encrypted secrets; upstream stdio MCP is disabled unless explicitly enabled because it can spawn host processes. A hosted service cannot automatically reach a user's laptop-only MCP services. [Selfhost configuration](https://github.com/UsefulSoftwareCo/executor/blob/a6a7bf2090ce103e37e38858f91fdd6fbce4afb0/apps/host-selfhost/executor.config.ts).

## Proposed implementation boundary

1. Zuse owns plugin identity, description, compatibility, optional instructions/skills, connection selection, project/session enablement, and uninstall semantics.
2. Executor owns upstream API schemas, credential storage/refresh, connections, tool execution, and server-side policies. Keep third-party credentials out of prompts and renderer state.
3. Each supported Zuse agent driver receives a scoped Executor MCP connection. Native skills/hooks remain explicit provider capabilities rather than silently claimed universal support.
4. Start with a controlled instance and two concrete workflows: read Linear/GitHub context and create a user-approved issue from both Claude Code and Codex. Test account isolation, blocked writes, approval denial, revoked tokens, and restart persistence before broadening the catalog.

## Zuse wiring to change

The user workflow should be: browse a plugin package, inspect its instructions and tool permissions, connect or select an account, then enable it for selected projects/agents. Install and account connection are separate state transitions. Claude Code already merges `userMcpServers` into its SDK configuration in `packages/agents/src/drivers/claude.ts`; Codex also has native MCP configuration support. The ACP extension driver currently supplies empty `mcpServers` arrays for both new and loaded sessions in `packages/agents/src/drivers/extension-acp.ts`. Thread resolved MCP configuration through that driver and negotiate transport support rather than assuming every adapter accepts the same endpoint. These observations were supplied by the parent investigation and should be checked against the implementation revision before editing.

## Release gates

Choose deployment ownership (personal/team instance versus Zuse-managed tenants), establish tenant-auth mapping and OAuth applications, verify image provenance, and test real Claude Code/Codex sessions including approval behavior. ACP requires explicit MCP forwarding/capability negotiation before advertising it. Neither a self-hosted service nor a portable plugin implementation has been delivered by this research.
